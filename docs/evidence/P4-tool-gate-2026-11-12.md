## 3 接口

~~~text
guardian.py
  TOOL_DENY_LEVELS = frozenset({"L3"})
  guardian_tool_check(name: str, args: dict, role: str = "", level: str = "") -> dict
      {"allow": bool, "reason": "ok" | "crisis_no_tool" | "unknown_tool" | "bad_args"}

agent_loop.py
  AgentResult(text, tool_calls, trace, usage, ok, error, sources)
  run_agent(system_prompt, history, tool_list,
            max_steps=AGENT_MAX_STEPS, *,
            chat=None, gate=None, source_filter=None,
            fallback_text="", deadline_s=AGENT_TOTAL_TIMEOUT_S)
  # 单次工具调用顺序：预算 → gate → tools.execute

panel.py
  render_trace(trace: list[dict] | None) -> None
~~~

门禁返回四态（顺序固定）：

| reason | 条件 | 结果 |
|---|---|---|
| crisis_no_tool | level == "L3" 或 role == "crisis" | 拒绝 |
| unknown_tool | tools.has(name) 为假 | 拒绝 |
| bad_args | args 非 dict / 缺 parameters["required"] 的键 | 拒绝 |
| ok | 其余 | 放行 |

L3 的第一道闸仍是 orchestrator 在 loop 之前短路（pre_check → short_circuit，根本不进生成）；门禁是第二道闸，两者都有测试。

## 6 与文档的偏差（行为不变）

1. P4 文档 §6 用 len(messages) == 2 判“第一次调用”，但 run_agent 首调 messages 只有 system（长度 1）。照抄会假通过，实际测试改 len(messages) == 1。
2. 文档的 loop 失败用例调 orchestrator.handle，但 P1 起 handle 向上抛、兜底只在 safe_run。测试改调 safe_run，断言（L2 / FALLBACK_LINE / listener / degraded / PIPELINE_FAILED）不变。
3. 文档只要求 _generate 返回 sources，但最终响应由 _log_and_result 组装。若不补 "sources"，app 永远拿不到来源；已在 _log_and_result 补。
4. 文档预计 test_fault.py 的 F-07 会红，实测 F-07 直接调 guardian_post_check，不经过 loop，未改。
5. agent.chat_with_tools 的 MOCK 分支忽略 _mock 的 ok/error（P2 旧简化），本轮不改；测试统一 patch chat_with_tools，不依赖该语义。
6. agent_loop._safe_sources 捕获来源过滤异常，只记异常类型名（不记内容），返回空来源；防工具结果形状异常把整轮打崩。

## 7 安全核对

- **只升不降**：L3 双保险（短路 + 门禁拒绝）；loop 失败不是“空回复”，而是 raise → safe_run 的 L2 模板 + PIPELINE_FAILED。
- **否决权唯一**：门禁在 tools.execute 之前，gate 异常 fail-closed；工具结果不能改 gate 结论。
- **责任不越界**：orchestrator 只传 gate/source_filter；guardian 不依赖 UI、不参与协商；agent_loop 不写记忆。
- **结果不可信**：工具返回只作资料；来源链接由 web.search_sources 生成、app 用代码渲染，模型正文里的链接不参与。
- **日志**：只记工具名 / 状态 / 耗时 / 条数；trace 的 detail 只有等级、角色、tools=N、pipeline。
- **可关**：AGENT_LOOP=0 回 v1 call_llm 管线，测试与冒烟均覆盖。
