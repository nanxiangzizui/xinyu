### 3.1 P7a 贴纸：从代码强制改成"想加就加"

**决策：不做随机化。** 随机贴纸仍然是"系统决定要不要加"，只是概率从 100% 降到 X%，读起来仍是机器节奏。改成**模型可选**：

1. `style.py` 删掉 `STICKERS` / `STICKER_LEVELS` / `_sticker()`（共约 12 行），`polish()` 变成 `_strip_period(_clip(text))`。
   - 为什么不留"机制"：`_.cursor/rules/xinyu.mdc` §8.3 —— 只有一个调用方（`orchestrator.py:222`）且没有第二个实现，留着的抽象只会变成下一个人重新打开的开关。
2. `style.SPEECH_RULES` 增一条（第 12 条）：`"表情不是每句都要：想用就用一个，不想用就不加，别拿它当句号。"`
3. `roles.py` 五张卡的 `emoji` 行改写（`roles.py:33` / `:48` / `:63` / `:78` / `:93`）：把"少，最多一条一个"这类**配额式措辞**改成默认态——`emoji: "默认不用；想用只用自家那一个，一条最多一个。"`
   - 依据：prompt 里的"上限"会被模型当配额（`style.py:44` 的"每轮只做一件事"就是这么失效的），只有"默认不用"这种**默认态**措辞能改行为。

**会变红的既有断言**（必须一起改，不许留着跳过）：`tests/test_style.py:59-63`、`:66-68`；证据脚本 `docs/evidence/p5_smoke_2026-11-12.py:51`、`docs/evidence/p6_scenarios_2026-11-13.py:67` 与 `:220`。

### 3.2 P7b 安全基线：两条漏掉的表达（需签字）

**改法一：DIAG 补"可能 / 一定"**（`guardian.py:143`）

```text
现在：r"(你(得|患)了|你有.{0,6}倾向|你是.{0,4}症|抑郁症|焦虑症|建议服药|吃药)"
改为：r"(你(得|患)了|你有.{0,6}倾向|你(可能|也许|大概|一定|肯定|就是|是不是)?.{0,3}(抑郁|焦虑)|你是.{0,4}症|抑郁症|焦虑症|建议服药|吃药)"
```

- 只加一条分支，其余原样；`抑郁症`/`焦虑症` 仍然单独命中（`你这是抑郁症` 不依赖新分支）。
- 风险面：DIAG 只扫**模型回复**，扫宽了只会多拦、不会漏拦 → 符合"只升不降"。
- 不扫用户原文：用户说"我肯定是得了抑郁症"是求助，不是诊断（这条由 H 组处理，见下）。

**落地回执（2026-11-16）**：实际实现把修饰词组的 `?` 去掉了，即改成**必选**：

```text
落地：r"(你(得|患)了|你有.{0,6}倾向|你(可能|也许|大概|好像|似乎|一定|肯定|就是|是不是).{0,3}(抑郁|焦虑)|你是.{0,4}症|抑郁症|焦虑症|建议服药|吃药)"
```

原因：留成可选时 `.{0,3}` 会把"你最近很焦虑吗 / 你说你很焦虑"这类**高频共情句**一并判成诊断口吻（都命中），每条都要走复核/重写。去掉 `?` 后两条签字用例仍命中（`你可能有抑郁倾向`、`你一定是抑郁了`），代价是"你有点焦虑"这类**无修饰的直陈句**仍漏——符合本项目"宁可漏不要误拦"的口径（`guardian.py:143` 上方注释已写）。另补了 `好像/似乎` 两个修饰词。

**改法二：W02 认"没意义"但只认带主语的**（`roles.py:230`）

```text
现在：r"(没意思|麻木|空落落|无所谓)"
改为：r"(没意思|麻木|空落落|无所谓|(我|人生|活着|日子|这一切).{0,4}没(有)?(什么|啥)?(意思|意义))"
```

- 保留裸 `没意思`（`metrics.TEN_TURNS` 第 5/8 轮靠它，`ROLES` 的 C-07 也用它）。
- 新分支要求主语在 `(我|人生|活着|日子|这一切)` 里，所以"这电影没意义"仍是 L1 —— 这是"宁可漏不要误拦"的落地口径。
- 为什么是 L2 不是 L3：这句话是绝望感，不是即刻危险；L3 留给 H10（`roles.py:221`，要求"活/死"）。`活着没意义` 仍由 H10 判 L3（H 组先于 W 组，天然只升不降，见 `guardian.py:80-109`）。
- 为什么必须动 W02 而不是只动 H10：`人生没什么意义` 里根本没有"活/死"，给 H10 加插入容忍也命不中。

**签字口径**：这两行改动会让 `contract_check` 仍过（它只校验规则**结构**：20 条、X5/H10/W5、正则可编译、顺序 X→H→W，不校验 pattern 原文），但**改了 RULES 第 20 条的内容**。按红线，动 `RULES` 要先拿到用户一句"可以"。

### 3.3 P7c 连发合并：把"13/15 是有意连发"变成能力

**先纠正一个前提**：用户连发不是 bug。第 13/15 行本来就是一口气说两段。真正的缺陷是——**第一段从来没被回应过**，第二轮只拿最后一条去生成（`app.py:168` 传的是本轮 `text`，不是整段话）。

**机制（零新状态、零额外延迟）**

Streamlit 在新输入到达时会中断正在跑的 run。这就够了：

```text
发 a       → run1：append user(a) → 生成中
发 b       → run1 被打断（没回复、没落库）→ run2 重跑
run2       → 历史末尾是 [user(a), user(b)] → 合并成一段 → 只生成一次 → 落一条 assistant
```

不需要定时器、不需要 `sleep`、不需要"等 1 秒"。"还没说完"由真实时序给出：没被打断就正常回，被打断就等你说完一起回。

**实现（三处，都在 `app.py`，188 → 约 205 行）**

1. `_merge_tail(messages) -> tuple[list[dict], str]`：从末尾往前收集连续 `role == "user"`，用 `"\n"` 连接成 `merged`，返回 `(messages[:-k] + [{"role": "user", "content": merged}], merged)`。
   - 喂给模型的 history 必须**只有一条** user：`orchestrator._generate` 走的是 `history[-10:]`（`orchestrator.py:73`）与 `run_agent(..., history[-10:], ...)`（`orchestrator.py:79`），`run_agent` 把 history 直接当上下文（`agent_loop.py:124`，当前这句话就在 history 末条里），多留一条 user 会让同一句话出现两次。
   - `merged` 也作为 `safe_run(text=...)` 的入参：`guardian_pre_check`、`coordinator_decide`、`memory.update_memory` 都以它为准——**判危必须扫整段**。
2. `turn` 只在回复落库后 +1（`app.py:162` 现在每条输入都 +1）。侧栏"第 N 轮"= 回答了几次，不是发了几条。
3. 先落库再渲染：把 `messages.append(assistant ...)`（`app.py:175-177`）挪到 `st.markdown(result["reply"])`（`app.py:170`）之前。这样即使在渲染那一帧被打断，重绘时回复还在；现在是"看见了但没记住"。

**UI：不合并气泡**。三条 user 仍渲染成三个气泡（`_render_history` 按 role 渲染，本来就支持），只有 assistant 出一条。顿挫感在视觉层，合并只发生在语义层。

**安全交互（必须断言）**

- 连发里夹着 L3：合并文本先过 `guardian_pre_check` → 命中 → 短路出模板 + 三张资源卡，不生成。比现在**更安全**（现在第一段根本没进判危）。
- L1/L2 的连发：一次回复、`pick_resources` 只出一次卡。
- 生成失败：`safe_run` 兜底不变；`turn` 不涨，pending 保留，下一次输入会连同它一起被理解 → 连发不会丢话。

## 5 P7d（默认不做）：回复侧分条

用户说"连发更有顿挫感"，我理解成**用户侧**（一次说几段，系统等你说完再回），已由 P7c 落地。**系统侧**主动分条（一条回复拆 2–3 个气泡 + 每条之间 `time.sleep`）不建议做：

- 它把"顿挫"从用户的真实行为变成系统的表演，这和建议里"别演"的方向相反；
- 真人口语本来就短，P7c 已经让系统少说；
- L3 模板与 FALLBACK 不能拆（拆了就破坏"逐字不变"），只拆 L1/L2 反而让"危机时最连贯"变成可观察的差别；
- 300 秒录屏里多一次等待就是多一处丢帧风险。

要留的话只留一句开关：`REPLY_SPLIT = 0`，实现推迟到"现场演示需要"再写。
